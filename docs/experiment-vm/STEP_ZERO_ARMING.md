# Which routes can arm the step-zero eval gate

Read this before being dispatched to arm the universal step-zero eval gate on
any route. It answers, per registered adapter contract, whether arming is
reachable today and what blocks it if not.

It exists because the answer has already been paid for twice, both times
mid-implementation:

- an agent dispatched to arm the gate for MageFlow declined, on the grounds
  that the family could not publish a valid step-zero artifact;
- an agent that wired the pre-mutation boundary for Qwen AO3 and RWKV
  post-training then declined to arm either, the sharpest blocker being that
  `posttraining_authoring()` declares no checkpoint output at all while
  eval-examples is checkpoint-bound by construction.

Both refusals were correct. Neither fact needed an implementation to discover.

One of them has since partly expired, which is the argument for generating this
table rather than writing it: **every stateful profile in the registry declares
an `evaluator` slot today, MageFlow included.** A build of `origin/main` at
`38fcaa17` shows an `evaluator` slot on all 20, and the MageFlow contracts also
carry `evaluation_schedule`, `artifact_renderer` and `qualitative_samples`. The
missing-evaluator claim was true of an earlier registry — a build predating the
MageFlow full-backbone contract shows MageFlow slots as optimizer, learning
rate, weight decay, gradient clipping and parameter router, and nothing else.
So the blocker moved while the note about it did not. What blocks MageFlow now
is the row below: no `eval_examples` output port.

## What arms the gate

`trainvm/src/service.cpp` computes `step_zero_eval_gate_required` as
`invocation_requires_step_zero_eval_gate(invocation->publishes)`. The predicate,
in `trainvm/src/eval_examples_contract.cpp`, is three conjuncts over each
publication's `declaration`:

```
declaration->value("required", false) &&
declaration->value("type", std::string{}) == "eval_examples" &&
declaration->value("schema", std::string{}) == kEvalExamplesSchema
```

All three must hold, and the predicate returns a bare `bool` with no
diagnostic. A declaration satisfying two of the three arms nothing and says
nothing.

`invocation->publishes` is assembled in `trainvm/src/adapter_invocation.cpp`:
for each entry of the workflow node's `publishes` map, the declaration is
`spec.artifacts[logical_name]` — an **artifact declaration in a composition
document**, reached through a node that publishes it. So arming needs two
separate things, which fail for different reasons and are fixed in different
files:

1. **An `eval_examples` output port on the adapter contract**, declared in
   `trainvm/src/rwkv_lab_worker_contract.cpp`.
   `trainvm/src/adapter_registry.cpp` rejects a node that "publishes undeclared
   operation output", and `require_artifact_contract` forces the published
   artifact's type and schema to match the port. Without the port, no
   composition can publish eval-examples at all.
2. **A shipped composition document** that declares the artifact with all three
   conjuncts and publishes it from the invoking node.

The seam between them is worth stating, because it is where this gate was inert
for the HF family: the *port's* `required` and the *artifact's* `required` are
different fields, and `require_artifact_contract` does not tie them. A required
port forces the node to publish something; only the artifact's own
`required: true` arms the controller. `trainvm/src/run_authoring.cpp` carries
the same note beside the HF checks.

## Two things that are not arming declarations

Both look like hits when grepping for `eval_examples`, and both are unrelated:

- `output_name="eval_examples"` in a worker's publish call — for example in
  `src/rwkv_lab/hf_multimodal_sft.py` — is the worker publishing at **runtime**.
  The gate reads authoring.
- `eval_examples: int = 64` in `vision_frozen.py`, `vision_native.py` and
  `vision_student.py` is a **count**: how many examples to evaluate. A
  grep-derived table reports three vision routes as arming and is wrong.

Neither can reach the table below, which reads no Python trainer source.

- *evaluator slot?* and *checkpoint output?* and *eval_examples output port* come

## What this table does not cover

It answers one question — *can this route arm* — and nothing adjacent. In
particular it is **not** evidence for any of the following:

- **That an armed route works end to end.** Arming makes the controller demand
  step-zero evidence. Whether the worker then produces a valid, non-empty,
  correctly-stepped eval-examples artifact, and whether a resumed attempt
  recovers gate satisfaction from journal or checkpoint evidence, is untested
  here.
- **That the pre-mutation boundary is crossed.** Being able to arm and calling
  `pre_optimizer_step` before mutating are different properties.
  `tests/test_step_zero_interception_enumeration.py` owns the second one, and
  its `UNMAPPED_INTERCEPTION` allowlist is where that debt is recorded. A route
  can be off that allowlist and still unable to arm, and the reverse.
- **That arming a route would be safe.** A route whose port and composition both
  satisfy the predicate can still deadlock fresh or resumed attempts if no
  producer publishes the artifact. This table says the declaration is reachable,
  not that the evidence exists.
- **Any route outside the worker's adapter registry.** The rows are exactly the
  operations `rwkv_lab.trainvm_adapters.handlers` dispatches, cross-checked
  against the pin. `trainvm.core` operations and anything authored outside that
  registry are out of scope.
- **Composition documents outside `docs/experiment-vm/examples/`.** A document
  living anywhere else — a test fixture, an operator's private plan — can arm a
  route with an eval_examples port without appearing in the *can arm today*
  cell. The cell means "a shipped example document arms it", which is the
  strongest statement that can be made from documents in this repository.

## Contract naming that does not resolve

Two shipped composition documents, `examples/mageflow-cache-resume.json` and
`examples/rwkv-scratch-topologies.json`, invoke contracts
`rwkv_lab.mageflow.v1.Train`, `rwkv_lab.mageflow.v1.CacheEncoders` and
`rwkv_lab.mageflow.v1.PrepareCacheSpan`. None of the three is in the adapter
registry, which declares the MageFlow family as
`rwkv_lab.mageflow_appearance_expert.v1.Train`,
`rwkv_lab.mageflow_terminal_expert.v1.Train` and
`rwkv_lab.mageflow_full_backbone.v1.Train`. Those documents therefore contribute
no row to the table and could not be authored against today's registry. That is
recorded rather than fixed here, and is tracked on its own card.
